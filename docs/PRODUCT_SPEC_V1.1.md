# Pokémon Shiny Tracker — Product Spec V1.1

- 状态：需求冻结（规划基线，不代表代码已实现）
- V1.0 冻结日期：2026-10-23；V1.1：正式纳入数据源策略与 GitHub 新仓库规范（不扩大功能范围）
- 范围：长期个人 Web 管理系统，覆盖全系列游戏的基本闪光记录；先本地单机运行。

## 1. 产品目标与边界
记录 Hunt 过程、闪光个体、收藏图鉴、随机 Hunt/Bingo、统计分析和历史 Excel 数据迁移。第一版不要求多用户、云服务器、账户系统、自动同步、原生桌面/移动 App。采用 Vue 3 + TypeScript + Vite + Element Plus + ECharts / Go + Gin + GORM / SQLite / Git；API 前缀 `/api/v1`。不在没有技术决策记录的情况下随意变更技术栈。

## 2. 核心模型及不变量
- `Hunt`：一个刷闪目标/活动，属性包括目标物种与可选形态、原始目标游戏、方法、可选起止日期、可选累计次数及其单位、可选耗时、状态（进行中、已完成、已放弃）、备注。一次 Hunt 可产生 0..N 个闪光成果，包含非目标意外闪光。
- `ShinyRecord`：实际拥有过的一只闪光个体对应一条永久身份记录，支持不关联 Hunt（历史 Excel / 交换获得）；同种多只各自有独立记录。记录原始获得物种/形态与当前物种/形态、最初获得游戏、当前保存位置、可选获得日期、来源（自刷、交换、活动、其他、未知）、个体信息及持有状态。
- `PokemonSpecies` 和 `PokemonForm`：稳定图鉴编号及形态 ID。物种和形态分开，不以字符串名称作为唯一关联主键。
- `Game`：独立游戏/版本实体，可标记主系列、衍生作品及本地名称。Pokémon HOME 默认作为保存位置/特定来源，非普通刷闪游戏；Pokémon Sleep 的收藏视为独立体系。
- `ShinyHistory`：轻量历史记录，至少支持进化、形态变化、持有状态变化；可进一步扩充跨游戏转移历史。不强制复杂事件溯源。
- `Attachment`：本地文件/视频链接关联，记录类型、位置、元数据和所有权；备份含附件。
- `ShinyAvailability`：按游戏及形态维护可合法刷闪性、来源、核对时间、覆盖状态（确认可刷、确认不可刷、未知）。
- `PokemonHuntMethod`：按游戏/形态维护已核实的方法、地点、条件、资料来源、更新日期；“确认可刷”与“已有方法攻略”互不等价。
- `HuntPlan` / `HuntPlanTarget`：保存筛选规则、生成时间、生成时快照、随机目标、目标游戏、格子、状态、关联 Hunt/成果。

## 3. Hunt 业务规则
累计次数为非负整数或空值，必须保留计数单位；耗时以标准数值单位储存，输入界面可换算。三种初期状态：进行中、已完成、已放弃。已完成原则上关联至少一个成果；已放弃不删除此前成果；进行中允许已有部分成果。更新累计值与记录每次增量不同：MVP 手动更新累计值，后续 `HuntSession` 支持分次记录和计时器。跨游戏/方法计数单位不兼容时不直接比较效率。

## 4. 个体业务规则
同一闪光的进化、传送不新增个体；原始获取游戏与当前位置分离。交换/活动所得也可记录，但不计为亲自刷闪成果。已交换出去/放生保留历史、从当前持有排除。未知日期、次数、游戏等允许空值，不填造假值。性格、个体值、球种、特性、等级、性别、昵称及其他不同世代字段可选。历史获得形态只能根据有据可查的原始记录或历史事件计算，不推断未记录的进化前形态。

## 5. 双层图鉴及统计
- 物种完成度：按全国图鉴编号去重，同物种不同形态只贡献一个物种目标。
- 形态完成度：按物种 + 有意义的持久形态计算；地区形态、可收藏的外观/形态变体可单独统计。一般性别微差、战斗中临时形态、超级进化、活动服装默认不纳入主形态完成度；仍可记录原始资料。
- 历史获得：有确凿个体或历史事件证明曾拥有该物种/形态；当前持有：以仍持有的个体当前形态计算。
- 可切换维度：物种/形态，历史/当前，主系列/全系列/指定游戏，合法可获取/完整资料展示。
- 分母来源：按相关范围确认存在合法可获取闪光的目标；未知或尚无途径默认不计入完成率分母，但允许录入个体及展示“待核实”。分母规则和资料版本可追溯。
- 数据未覆盖时不能宣称相关游戏的图鉴完整度准确覆盖全部目标；需显示覆盖说明。

## 6. 游戏范围
MVP 接受第一至第九世代主系列及相关重制作品、Let's Go、Legends、Pokémon GO、Pokémon Sleep 和可配置的其他游戏的基本记录。特殊游戏机制/专属图鉴及概率系统后续完善。保留新增未来游戏的扩展能力，不编造未公布资料。游戏获取来源与当前位置不混淆。

## 7. Hunt Planner（正式模块）
### Random Hunt
选择一个或多个游戏；默认按照“全系列历史未获得”抽取，允许切换“选定游戏原始获得记录中未获得”；支持物种或形态维度、指定数量，默认排除进行中的同目标 Hunt、不重复抽取。只有已确认在所选游戏中直接合法可刷的目标才进入候选池；确认可以刷但具体攻略缺失时仍可抽中，显示“方法待完善”。先物种/形态去重均匀抽样，再确定可选游戏，避免多版本权重偏斜。候选不足要报告实际数量，不补入不合法目标。生成结果可保存或转成 Hunt，不自动批量创建 Hunt。
### Hunt Bingo
3×3 和 5×5，默认没有免费格；可持久化多张卡；每格不重复；格子可开始/关联 Hunt；未开始格可重抽，已完成格不可静默重抽；行/列/对角线自动判定。默认由挑战创建后亲自合法获得、符合目标物种/形态和游戏的 ShinyRecord 完成；旧收藏、单纯传送、交换默认不算。日期精度不足时标记需人工核验，不能自动判断通过。结束/放弃的挑战保留历史。

## 8. UI 与数据管理
一级导航：首页总览、刷闪任务、闪光收藏、闪光图鉴、Hunt Planner、统计中心、数据管理、系统设置。桌面优先、响应式 Web；默认简体中文、浅深主题；资料预留多语言，但不要求 MVP 具备完整多语言 UI。第三方图片失效时有占位，外部资源许可和稳定性待核验。
Excel 导入必须有表头识别、字段映射、预览、数据验证、重复候选提示、错误报告、批次追踪与导入结果校验；无 Hunt 的历史记录直接生成 ShinyRecord。不以相同宝可梦+游戏+日期直接断言重复。导出和备份需要核对数据与附件的一致性；破坏性覆盖/恢复要求用户授权。

## 9. 宝可梦权威资料与数据集成策略（V1.1 新增，ADR-016）

### 9.1 目标及分工
- **PokéAPI（v2，主结构化来源）**：全国图鉴物种、宝可梦/形态标识、进化关系、部分游戏/遭遇结构化数据。优先使用其稳定 ID/标识建立外部引用，但系统内部建立自己的不可变主键，不假设外部 form ID 等于全国图鉴编号。优先读取该来源的多语言名称；中文名称和形态本地化与 52Poké 对照核验。
- **神奇宝贝百科（52Poké，中文名称和资料校验）**：用于官方简/繁中文译名、地区形态及个别游戏的获取信息交叉校验。先验证可使用的接口/访问方式、机器读取规则和许可条件；不能预设存在开放且适合大规模导入的专门 API。
- **Serebii（游戏机制与闪光核验）**：用于各游戏特定获取方式、闪光锁定、出现条件、遭遇机率、闪光机率及其适用前提的人工/合规核验。无明确许可时不得将批量抓取 Serebii 当作计划默认实现。
- **Bulbapedia、Pokémon Database、宝可梦官方公告和游戏内资料**：交叉核验游戏专属机制、事件或差异。核验冲突时保留证据和争议状态，不静默选择方便的数值。

### 9.2 游戏遭遇率与闪光率是不同数据
- “在游戏中存在/可获取”、“该来源能否闪光”、“该地点遭遇概率”、“符合特定条件的闪光概率”必须分别建模，不得混为一个概率字段。
- `ShinyAvailability` 的直接刷闪判定须至少支持 `confirmed_available`、`confirmed_locked`、`transfer_only`、`unknown`；方法和概率资料缺失不得被误判为锁闪。
- `PokemonHuntMethod` 表示按游戏版本、物种/形态、方法/地点/前置条件有效的刷闪路径；概率作为附属的条件化规则（可为空），需注明基础率、加成前提、版本/活动时间范围以及来源。出现概率和闪光概率分开储存，概率不可靠时显示未知。
- 同一种宝可梦在多个来源/版本中存在的获取规则，应保留分别可追踪的记录，不用后来的数值覆盖另一个方法的规则。

### 9.3 本地数据与资料溯源
- 采用“外部来源 → 采集/人工录入 → 暂存校验 → 审核差异 → 本地 SQLite 资料表”的更新流程。用户浏览图鉴、记录 CRUD 与 Hunt Planner 必须可以离线使用本地已核实数据，不强制每次访问网络。
- 至少保留来源名称、原始 URL/外部标识、引用字段、采集时间、最近核对时间、数据版本/批次、状态（未核实/已核实/有争议），必要时保留适用游戏和条件。设资料覆盖率及待核实提示。
- 不通过更新基础资料改变个人历史 `Hunt` / `ShinyRecord` 的含义或 ID；外部 ID 与内部 ID 的映射应可维护。
- 资料更新需先展示变化、进行校验、保证原子应用，并提供恢复到上一资料快照/批次的机制。更新失败不得破坏现有可运行数据。
- API 中断或游戏尚无已核实资料时，基础记录仍可正常创建；随机池仅使用已验证、适用游戏范围内直接合法可刷的目标，明确候选池覆盖范围。

### 9.4 合规边界
- PokéAPI 官方文档要求本地缓存、友善控制请求频率；不以其“无认证”推论能无限制抓取。
- 52Poké 的机器读取规则涉及 robots.txt、可识别的 User-Agent、不可并发与请求间隔等具体约束；实际开发前再次核验最新版本并遵守。
- 对 Serebii、其他百科和图片/文字资料，只用可合法复用的内容与数据形式；未核实批量授权则仅留人工核对记录和外部来源链接。不默认镜像整个网站/图片集。
- 中文名、截图及宝可梦图片等需分别核验内容版权、许可与署名要求，不假设百科开放读取就等于所有内容可再分发。

### 9.5 正式执行 Task
T006 负责可离线使用的基础图鉴/游戏种子数据与本地引用；T016 完善形态、名称本地化、来源映射与数据覆盖；T026 在可核验范围内补充游戏可获取性、获取方法和条件概率；T027 仅查询通过验证的本地候选池；T024 再实现受控增量更新、差异预览及回滚。详见 `DATA_SOURCE_POLICY_V1.1.md`。

## 10. 非功能要求
- 数据完整性：外键、必要索引、迁移及可恢复性测试。
- 可维护性：分层清晰、避免过早复杂化；重大设计记录 ADR。
- 自动测试：实体及状态、API、图鉴口径、随机池、Bingo 判定、导入去重、回归。
- 安全边界：本地优先、默认限制非授权远程访问；不对未经授权的数据执行破坏性操作。
- 不承诺 AI 普通对话结束后仍会持续后台编码；自动连续执行依赖具备仓库及工具权限的工作环境。
