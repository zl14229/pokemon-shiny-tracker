# Hunt Bingo（T028）

创建入口 `/#/planner/bingo`，已保存卡片在 `/#/planner` 的计划历史中。每张卡片持久化 3×3 或 5×5 个唯一目标，无免费格。候选复用 [Random Hunt](PLANNER.md) 的双缺失池、已核实直接可刷子集、多版本先去重均匀抽样和默认排除进行中规则。

**正式初始资料只有 12 个唯一目标。** 可用目标达到 9 时能建立 3×3；当前不足 25，5×5 会明确拒绝，不能用重复、锁闪、仅传送或未知补格。完整 5×5 的存储、25 格完成、12 条连线和备份恢复通过隔离合成资料测试，不冒充已核实的正式游戏覆盖。

## 卡片与格子

- 创建后立即保存，可有多张卡片。生成请求 request_id 幂等，不自动创建 Hunt。
- 未开始格可以明确重抽；排除本卡所有现有目标及本次旧目标。无替代目标则整个操作取消；原目标保留审计历史。
- 重抽要求期望的 target_key 与请求标识，避免另一页面已换目标后仍错误操作。请求重试不会额外重抽；界面在不明结果后读取当前状态，旧目标未变时复用原请求、目标已变时下一次明确操作使用新请求。
- 可以开始此格创建 Hunt，或关联目标、游戏、形态均符合的进行中 Hunt。已关联目标重复操作返回原 Hunt。开始与格子完成都不复制 ShinyRecord；挑战不会代替用户修改 Hunt 的完成状态。
- 已开始或已完成格不允许重抽。服务端先检查尚未同步的新成果，不能通过先重抽绕过实际已满足的完成条件。
- 根据行、列和两条对角线自动计算连线。形成连线后可以继续挑战，也可明确“结束已连线挑战”；全格完成自动结束。未连线不得直接结束为完成。
- 任意进行中的挑战可放弃，保留格子、已完成成果、关联 Hunt 和审计历史。结束后不重新抽取、不改写完成证据。放弃卡片不会自动放弃可能被其他计划使用的 Hunt。

## 默认完成证据

打开卡片和点击“核对新成果”会对本地个人记录进行核验。只确认同时满足以下条件的成果：

1. 是挑战创建后登记的新永久个体，未软删除；来源明确为 self_hunted。交换、活动、其他或未知来源不自动当作亲自刷闪。
2. 原始获得物种与所选游戏明确且匹配。不会用当前保存位置替代原始游戏，也不会从后续进化推断未被记录的该目标在指定游戏的新获得。
3. 原始形态明确，且该游戏和形态在当前本地资料中有 verified、confirmed_available、direct_hunt=yes、纳入收藏形态的来源证据。即使是物种格，原始形态未知也不能推测合法性；形态格还须精确匹配形态。
4. 获得日期有 YYYY-MM-DD 精度，按挑战创建时保存的日历时区，**严格晚于创建日**且不在未来。只有年／月、缺失日期或创建同日仅有日期，均不自动判断通过。
5. 一个个体在同一张卡只完成一个格子。只根据原始获得目标确认成果；已确认成果之后的持有变化不会产生第二个体或重复完成。

旧收藏即使后来补填、转入目标游戏或修改当前形态，也不能成为挑战后的新获得。反之，新获得后转出或交换出去仍保留当时已获得的证明，不要求当前仍持有。

## 显式人工时间核验

对于原始身份、来源、游戏、形态及合法性均已明确，只有时间精度不足的记录，界面提供“补充时间并人工核验”。用户须选择个体、输入具体获得时间、填写核验依据并明确确认亲自合法获得。

补充时间必须晚于挑战创建、不能在未来，并与个人记录已知的年／月／日一致。此操作只解决日期精度，**不能覆盖旧个体、交换、来源不明、原始目标／游戏不匹配或未经核实的合法性**。具体时间与说明作为“用户核验”存入卡片完成证据，不将其标成官方资料，也不覆盖 ShinyRecord 的日期或来源。重复提交同一证据幂等；已完成格的证据不可静默替换。

日历时区由创建界面的浏览器提供，服务端使用经验证的 IANA 时区并保存，API 省略时为 UTC。比较日期使用该固定时区；具体补充时间带时区偏移转换为 UTC 存储。界面说明本机输入时区。不能从某日的零点假造实际获得时间。

## 持久化与资料变化

schema 9 新增 bingo_challenges（日历时区、尺寸、不可变创建时间）和 bingo_events（创建、关联、重抽、成果、完成／放弃审计）。计划、格子与来源快照继续使用 T027 表；完成证据保留个体 ID、原始身份、日期或人工时间、核验方式和来源批次。

刷新时重新验证当前可刷资料。资料缺失／撤回不自动完成；来源或映射损坏则失败并提示，事务内不部分确认。完成后的证据是当时的历史快照，不因后续编辑、软删除个体或资料变化而静默抹除；可查看原始核验依据和版本，但不宣称这些旧快照就是当前资料。

备份／导出包括 20 张表中的卡片与审计表，5×5 全格卡片恢复到新目录后保持目标、个体关联、连线和历史。旧版本备份须用对应旧程序先恢复新目录，再用当前版本升级，禁止覆盖真实数据库。

## API

均以 `/api/v1/planner` 为前缀，严格 JSON、同源约束；错误沿用标准信封。

- `POST /bingo`：`{request_id,rules,size:3|5,calendar_zone}`。count 由尺寸决定；不足返回 409 insufficient_candidates，不创建半张卡。
- `GET /plans/:id`：返回完整有序目标、创建时规则／覆盖、bingo 的尺寸、创建时间、时区、连线、每格核验原因／证据及历史。
- `POST /plans/:id/refresh`：空 JSON，核对新成果；封存挑战只读返回历史。
- `POST /plans/:id/targets/:target/hunt`：可选 hunt_id，Bingo 必须提供 expected_target_key。
- `POST /plans/:id/targets/:target/reroll`：`{request_id,expected_target_key}`，仅未开始格。
- `POST /plans/:id/targets/:target/verify-date`：`{record_id,obtained_at:ISO8601,evidence_note,confirmed:true}`，仅显式时间核验。
- `POST /plans/:id/close`：`{status:"completed"|"abandoned"}`，同一终态幂等，禁止改写另一终态。

GET 不会生成卡片或完成格子。刷新是显式 POST，界面打开卡片时自动执行；没有后台定时联网或持续刷取。
